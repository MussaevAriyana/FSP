# ФСП Карьера — документация

Платформа подбора ИТ-специалистов для Федерации спортивного программирования: кандидат получает **категорию** (специализация × грейд) по результатам теста, а работодатель **сам находит** подходящего человека в категоризированной базе и отправляет ему предложение с вилкой зарплаты.

## 2. Архитектура

### 2.1 Функциональная схема

```
                       ┌────────────────────────── Браузер (SPA, без внешних зависимостей) ──────────────────────────┐
                       │  Кандидат: профиль · опрос · тест · результат · приглашения · вакансии · микрозадачи · настройки │
                       │  Работодатель: потребность · банк кандидатов · «почему» · приглашение · вакансии · микрозадачи   │
                       └───────────────────────────────────────────┬──────────────────────────────────────────────────┘
                                                                   │ JSON / JWT (HTTPS)
┌──────────────────────────────────────────────────────────────────▼──────────────────────────────────────────────────┐
│ Flask-приложение                                                                                                    │
│  apidoc.Api — роутинг, проверка роли, валидация Pydantic, единый формат ошибок, генерация OpenAPI + Swagger UI      │
│  ┌ routers/auth ┐ ┌ routers/candidate ┐ ┌ routers/employer ┐ ┌ routers/public ┐                                    │
│  └──────┬───────┘ └────────┬──────────┘ └────────┬─────────┘ └───────┬────────┘                                    │
│         └───────────────┬──┴─────────────────────┴───────────────────┘                                              │
│  services:  domain (правила видимости, жизненный цикл теста, смена грейда)                                          │
│             testgen (семейства заданий) → engine (сборка теста, проверка, подтверждённый стек, флаги)               │
│             matching (категория → профиль → объяснение)   fsp (адаптер реестра ФСП)   resume (PDF ⇄ профиль)        │
└───────────────┬───────────────────────────────────────────────┬────────────────────────────────┬──────────────────┘
                │ SQLite (stdlib)                                 │ data/fsp_registry.json         │ SMTP
                ▼                                                 ▼ (замена: HTTP-API ФСП/Keycloak) ▼ (в DEV_MODE — лог)
```

### 2.2 Компоненты

| Компонент | Ответственность |
|---|---|
| `app/apidoc.py` | Микрослой над Flask: декоратор `api.route(...)` одновременно задаёт маршрут, роль, схему тела/параметров (Pydantic) и описание для OpenAPI. Документация не может разойтись с кодом — она строится из него (тест `test_openapi_covers_all_routes`). |
| `app/schemas.py` | Все входные модели и их правила (вилка зарплаты 1 000–10 000 000 ₽ и `до ≥ от`, пароль: буквы+цифры, обязательность согласия и т.д.). |
| `app/security.py` | Пароли — scrypt с индивидуальной солью, сравнение за постоянное время; JWT (HS256) с TTL. |
| `app/db.py` | SQLite, схема, тонкие помощники `q1/qa/ex`. Таблицы: `users, candidates, employers, test_attempts, grade_history, needs, vacancies, invites, applications, microtasks, microtask_assignments`. |
| `services/testgen.py` | 32 параметрических семейства заданий и пул концептуальных вопросов (§4). |
| `services/engine.py` | Сборка теста по «чертежу» сложности, проверка ответов, подтверждённый стек, флаги подозрительности. |
| `services/matching.py` | Коэффициент категории, сила профиля, объяснение. |
| `services/domain.py` | Правила, где сходятся все данные: кто что видит, когда можно начать тест, как присваивается категория. |
| `services/fsp.py` | Контракт реестра ФСП и расчёт силы достижений. |
| `services/resume.py` | Разбор PDF-резюме и генерация PDF профиля (reportlab, шрифт DejaVu — кириллица). |
| `app/static/*` | SPA на чистом JS: хеш-роутинг, делегирование событий, без CDN и сборки — работает офлайн. |
| `scripts/seed.py`, `simulate.py`, `validate.py` | Демо-данные, модель синтетического кандидата, процедура валидации. |

### 2.3 Почему такой стек

Хакатонное окружение, в котором велась разработка, закрывало PyPI, поэтому вместо FastAPI/SQLAlchemy использованы Flask, Pydantic и SQLite из стандартной библиотеки; недостающее (OpenAPI, валидация ответов-ошибок) реализовано в `apidoc.py` на ~200 строках. Для продакшена SQLite заменяется на PostgreSQL изменением слоя `db.py` — SQL в проекте стандартный, без диалектных расширений.

## 3. Роли, безопасность, персональные данные

- **Разделение ролей.** Роль проверяется на сервере для каждого маршрута; кандидат не может вызвать методы работодателя и наоборот. Данные другого пользователя недоступны по идентификатору (проверка владельца: приглашение, вакансия, попытка теста — отдельные тесты изоляции).
- **Псевдонимность.** Работодатель видит кандидата как `C-XXXXXX`. Фамилия, контакты и точный город скрыты до принятия приглашения; город показывается, только если кандидат разрешил, и по нему же работает фильтр (нельзя вычислить скрытое значение фильтрацией).
- **Публикация.** Кандидат попадает в банк, только если у него есть категория **и** согласие на публикацию. Настройки приватности: показывать стек / достижения ФСП / опыт / город; можно скрыться из банка, оставив возможность откликаться на вакансии.
- **Контакты.** Раскрываются в двух случаях: кандидат принял приглашение; кандидат сам откликнулся на вакансию. Отклонённое приглашение контакты не раскрывает.
- **Аутентификация.** Подтверждение e-mail, блокировка входа после 5 неудач за 15 минут, JWT с ограниченным сроком, заголовки безопасности (`X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`); весь вывод в интерфейсе экранируется.
- **152-ФЗ.** Согласие фиксируется при регистрации (дата хранится), отдельный переключатель публикации, выгрузка всех данных (`GET /api/candidate/export`), удаление аккаунта с каскадом (`DELETE /api/auth/account`, подтверждается паролем).
- **Антиспам.** Работодатель — не более 25 приглашений в сутки (`INVITES_PER_DAY`), микрозадач — 2 в неделю.

## 4. Категоризация и тестирование

### 4.1 Путь кандидата

1. **Опрос:** отрасль, специализация, технологии, самооценка грейда, формат работы. Самооценка нужна только как *запрос* — какой тест предложить.
2. **Выбор грейда:** стажёр / junior / middle / senior.
3. **Тест** на выбранную специализацию и грейд (12 заданий, 40 минут).
4. **Результат → категория.** Зачёт присваивает категорию и подтверждает стек. Незачёт **ничего не отнимает**: платформа предлагает пройти тест на ступень ниже (а при результате ≥ 85% — на ступень выше).

### 4.2 Генерация заданий

Банк фиксированных вопросов быстро «утекает» (его выкладывают в чаты и пересказывают). Поэтому основная часть заданий **не хранится, а порождается**: семейство задаёт шаблон условия, а **числа, строки, структуры данных и варианты ответа выбираются заново для каждой попытки** (зерно — `seed` попытки). Правильный ответ вычисляется кодом — выполнением сгенерированной программы, SQL-запроса к сгенерированной таблице, `ipaddress` для CIDR и т.п.; поэтому он не может «разойтись» с условием.

Семейства (32 параметрических: 11 общих и специализированные, часть которых разделяется между специализациями): трассировка Python-кода, оценка числа операций (O-нотация), бинарный поиск, подсчёт обменов сортировки, симуляция структур данных, SQL по сгенерированной таблице, регулярные выражения, битовые операции, графы, динамическое программирование, CIDR — общие; rate-limiter, задержка кэша, шардирование, backoff, закон Литтла — backend; специфичность CSS, блочная модель, массивы JS, event loop — frontend; статистика, матрица ошибок, байесовский вывод, масштабирование — data; cron, права chmod, SLA, выкатка, grep — devops; классы эквивалентности, покрытие, дефекты — QA. К ним добавляется небольшой **пул концептуальных вопросов** (не более 3 из 12, у него пониженный вес выбора) — единственная статичная часть.

### 4.3 Сопоставимая сложность и объективность

- **Чертёж сложности.** Каждый грейд имеет фиксированный состав по уровням заданий (1–4):

  | Грейд | Состав теста |
  |---|---|
  | стажёр | 8×ур.1 + 4×ур.2 |
  | junior | 3×ур.1 + 6×ур.2 + 3×ур.3 |
  | middle | 3×ур.2 + 6×ур.3 + 3×ур.4 |
  | senior | 2×ур.2 + 4×ур.3 + 6×ур.4 |

  Два кандидата одного грейда получают разные задания **одинаковой структуры сложности**. Вес задания равен его уровню; не более двух заданий одного семейства в тесте.
- **Критерий зачёта:** взвешенная доля баллов ≥ 65% **и** верно решена половина «ключевых» заданий целевого уровня (для senior — две трети: у старшего грейда нет уровня выше, и без этого условия его тест слабее отличал middle, см. §6).
- **Объективность:** проверка полностью автоматическая и детерминированная; числовые ответы принимаются с допуском, заданным в семействе; разбор с верными ответами показывается *после* сдачи — он ничего не раскрывает другим, потому что у другого человека будут другие числа.

### 4.4 Почему передача заданий не работает

| Сценарий | Что происходит | Мера |
|---|---|---|
| «Скинь мне вопросы и ответы» | У другого кандидата другие числа/данные: чужие ответы неверны. Модель: подстановка *идеальных* ответов друга даёт в среднем 3–4% (§6, раздел E). | Генерация по попытке |
| Утечка условий в чат | Условие без чужих чисел бесполезно; «слитый» банк из 300 попыток закрывает в среднем 8–24% заданий нового теста, ни разу не весь тест (§6, раздел A). Остаточный риск — пул концептуальных вопросов (около 15 на специализацию) и семейства уровня 1 с малым пространством ответов. | Ограничение пула ≤ 3 вопросов, расширенные пространства параметров |
| Повторные попытки «на разведку» | Не более 5 попыток в сутки, одна активная, таймер на сервере (дедлайн хранится в БД, а не в браузере); каждая попытка — новый вариант | Лимиты |
| Подбор «наугад» | Числовые ответы не угадываются; вероятность зачёта при случайных ответах ≈ 0% (§6, E) | Числовой ввод, веса |
| Подсказка в реальном времени (человек решает за кандидата) | **Технически не устраняется любым онлайн-тестом.** Снижаем стимул и повышаем заметность: флаги `too_fast` (< 10 с на задание), `many_tab_switches` (≥ 6 уходов со вкладки), `late`; при флаге вес профиля в подборе снижается на 15%, работодатель видит пометку | Флаги, вес профиля |

### 4.5 Ограничения смены грейда

- Повторная попытка **той же** категории разрешена всегда (в пределах суточного лимита).
- Первое присвоение категории свободно; затем 24 часа «окна калибровки», когда можно один раз пересмотреть выбор (человек мог ошибиться при самооценке).
- Дальше смена грейда или специализации — не чаще раза в `GRADE_COOLDOWN_DAYS` (по умолчанию 90 ≈ 3 месяца). Интерфейс показывает дату, когда смена станет доступна.
- Провал теста никогда не понижает грейд.

### 4.6 Подтверждённый стек

Стек определяется не списком, который назвал кандидат, а **результатом по темам**: технология считается подтверждённой, если по связанной теме верно ≥ 66% (при ≥ 2 заданиях) либо решено задание уровня ≥ 3. Работодатель видит отдельно «подтверждено тестом» и «заявлено кандидатом (не подтверждено)».

## 5. Подбор (матчинг)

Работодатель описывает потребность: специализация, грейд, стек. Далее:

1. **Рекомендованные категории.** Показываются категории из банка с коэффициентом K ≥ 0.2 и числом кандидатов в каждой.
2. **Оценка кандидата:**

   ```
   итог = K(категория) × (0.15 + 0.85 × P)
   P    = 0.35·тест + 0.30·подтверждённый_стек + 0.25·ФСП + 0.10·актуальность
   ```
   - **K(категория)** — главный множитель: совпадение 1.0; соседний грейд той же специализации 0.55–0.60; через ступень 0.20–0.25; смежная специализация — вес связи (например backend↔devops 0.35) × коэффициент грейда. Кандидат «не той» категории не обгонит подходящего за счёт сильного профиля.
   - **тест** — нормированный результат: (доля − 0.65) / 0.35.
   - **подтверждённый_стек** — доля запрошенных технологий, подтверждённых тестом.
   - **ФСП** — «сила» участия: 35% объём, 40% лучшее относительное место, 25% давность (окно 3 года). Нет истории → 0, но **категория не страдает**: множитель K от ФСП не зависит.
   - **актуальность** — давность активности (окно 120 дней) и оценки микрозадач.
   - Флаг подозрительного прохождения умножает P на 0.85.
3. **Объяснение.** Для каждого кандидата возвращается список факторов с числом и текстом («подтверждено 2 из 3: python, sql», «топ-9.4% на Открытом кубке ФСП», «истории ФСП нет — не снижает категорию»). В интерфейсе — кнопка «почему».
4. **Фильтры** (специализация, грейд, стек, минимальный тест, город, «есть ФСП») сужают выдачу; счётчик «Найдено» отдельно хранит размер исходной выборки, чтобы работодатель видел, сколько кандидатов отсекли фильтры.

Самоописанное резюме (опыт, роли, soft skills) показывается в карточке с пометкой «заполнено самим кандидатом и не влияет на ранжирование».

## 6. Валидация

### 6.1 Что и зачем проверяем

У нас нет реальных кандидатов и разметки грейдов, поэтому проверяется **конвейер** (генерация → проверка → порог → категория → подбор) на синтетической популяции. Для каждого вопроса ТЗ — своя проверка:

| Вопрос | Проверка (раздел результатов) |
|---|---|
| Тесты нельзя переслать? | Доля совпадающих заданий между двумя попытками; покрытие нового теста «слитым» банком из N попыток (A) |
| Варианты одного грейда одинаково сложны? | Ожидаемая доля баллов для кандидата фиксированной способности по 400 вариантам: среднее и разброс (B) |
| Тест различает грейды? | Матрица «истинный грейд × проходимый тест» (C) |
| Результат воспроизводим? | Повторное прохождение: согласие зачёт/незачёт, κ Коэна, корреляция долей баллов; устойчивость присвоенной категории (D) |
| Тест устойчив к недобросовестным способам? | Случайные ответы; списывание идеальных ответов друга (E) |
| От допущений модели зависят выводы? | Анализ чувствительности (G) |
| Подбор лучше, чем по резюме? | P@10 и nDCG@10 против ранжирования по самоописанию при разной доле завышений (F) |

### 6.2 Модель кандидата

`scripts/simulate.py`: у кандидата скрытая способность θ; вероятность верного ответа на задание уровня L — логистическая функция от разности θ и сложности уровня (+ угадывание 25% на заданиях с выбором). Специалист грейда *g* имеет θ = g + 1.2 (+ шум 0.35), то есть **уверенно решает задания уровня g+1** — это допущение-определение «что такое грейд». Анализ чувствительности (раздел G) показывает, как меняются выводы при сдвиге 0.6–1.5.

Запуск: `python3 scripts/validate.py` (≈1 минута, детерминирован, seed = 2026) → `docs/VALIDATION_RESULTS.md`, `docs/validation_results.json`.

### 6.4 Как читать результаты (выводы и найденные слабости)

- **Передача заданий не помогает.** Два случайных теста совпадают по заданиям на доли процента; списывание идеальных ответов даёт ≈ 3–4% баллов; случайные ответы не проходят порог.
- **Утечка не нулевая.** Самая уязвимая — категория «стажёр» (уровни 1–2 с малым пространством ответов и пул концептуальных вопросов): слитый банк из 300 попыток закрывает в среднем около четверти задания теста, максимум — более половины. Полностью закрытых тестов нет, но для стажёрского уровня **нужно расширять семейства и пул** — это первая задача после запуска.
- **Валидация нашла дефект и мы его исправили.** Первая версия: у senior не было уровня выше 4, и тест на senior проходили ≈ 70% специалистов middle. Добавлено усиленное условие по ключевым заданиям (две трети), доля упала до ≈ 50% — **этого всё ещё недостаточно**, поэтому тест senior требует расширения диапазона сложности (уровень 5) и реальной калибровки.
- **Надёжность умеренная.** κ повторного прохождения 0.15–0.30 при 12 заданиях: результат на границе порога колеблется. Практический вывод для продукта: повторная попытка той же категории разрешена, а решение о смене категории не должно основываться на одном результате вблизи порога. Увеличение числа заданий до 16–24 в модели почти не повышает надёжность — главный источник шума здесь сам порог, а не длина.
- **Подбор: честная картина.** Если *все* кандидаты честно оценивают грейд, ранжирование по резюме точнее (оно получает правильный ответ «бесплатно»). Когда доля завышающих самооценку растёт до 50% и выше, платформа начинает выигрывать, и разрыв растёт. Это и есть заявленная ценность: категория не зависит от того, что человек о себе написал.

### 6.5 Ограничения валидации (что делать с реальными данными)

1. Все цифры — **на модели**; они проверяют логику, а не то, что задания измеряют именно «грейд». Содержательную валидность можно показать только на реальных кандидатах с экспертной разметкой.
2. Допущение θ = g + 1.2 произвольно (раздел G показывает зависимость). По реальным данным сдвиг, порог зачёта (0.65) и доли в чертеже подбираются заново.
3. План калибровки: (а) пилот на 100–200 участниках ФСП с известными результатами соревнований; (б) анализ каждого семейства по доле верных ответов и корреляции с общим результатом, исключение «слишком лёгких/слишком шумных» семейств; (в) экспертная проверка 5–10% заданий на однозначность условия; (г) пересчёт порога по кривой «доля зачёта при известных грейдах»; (д) регулярный мониторинг утечки — частота совпадений ответов в попытках разных людей.
4. Модель не учитывает осознанные «ферм-аккаунты» и совместное решение в реальном времени — это ограничение любого онлайн-тестирования без прокторинга (§4.4).

## 7. Интеграция с ФСП

### 7.1 Контракт

Документации API ФСП в рамках хакатона нет, поэтому определён минимальный контракт реестра, на котором работает платформа. Запись участника:

```json
{
  "fsp_id": "FSP-100001",
  "email": "user@example.org",
  "full_name": "Имя Фамилия",
  "events": [
    {"id": 10, "title": "Открытый кубок ФСП", "type": "contest",
     "date": "2026-06-04", "place": 17, "participants": 200, "points": 46}
  ]
}
```

Интерфейс адаптера один: `registry.get(fsp_id) → запись | None` (`services/fsp.py`). Реализация MVP — `FileRegistry` поверх `data/fsp_registry.json` (синтетические данные; файл перечитывается при изменении).

### 7.2 Привязка профиля

```
Кандидат вводит FSP ID ──► POST /api/candidate/fsp ──► registry.get(id)
                                         │ e-mail записи == e-mail аккаунта?
                                    да ──┴── нет → 403 `fsp_email_mismatch` (ID не найден → 404 `fsp_not_found`; уже привязан к другому аккаунту → 409 `fsp_taken`)
                                    │
                         сохранить fsp_id ► summarize(events) ► {top%, число мероприятий, сила 0..1}
```

Проверка совпадения e-mail нужна, чтобы нельзя было привязать чужой ФСП ID и «присвоить» чужие достижения.

### 7.3 Целевая схема (после MVP)

```
Браузер ──(Authorization Code + PKCE)──► Keycloak ФСП ──► id_token { sub, email, fsp_id }
Платформа (клиент OIDC) ── принимает токен, привязывает профиль по sub/fsp_id (ввод вручную не нужен)
Платформа ── GET {FSP_API}/participants/{fsp_id}/events (service token) ──► кэш на 24 ч ──► summarize()
```

Замена затрагивает два места: `verify_link` (проверка по токену вместо e-mail) и `FileRegistry` (HTTP-клиент с кэшем и таймаутами). Кандидат без истории ФСП (`events` пуст или записи нет) обрабатывается везде одинаково: сводка `None`, составляющая «ФСП» в оценке равна 0, в карточке — «истории ФСП нет», категория не меняется.

## 11. Развитие за пределами MVP

- **Защита от «фейковых» вакансий и рассылок.** Верификация компании (ИНН, домен e-mail), лимиты приглашений по репутации, жалобы кандидатов и «рейтинг ответа» (какую долю приглашений работодателя принимают), ручная модерация новых аккаунтов.
- **Интеграция с ATS** (Хантфлоу, Potok, Talantix и др.): передача принятых кандидатов в воронку, вебхуки статусов.
- **Прокторинг по желанию работодателя:** повторная короткая сессия на видео для кандидатов, дошедших до финала, — закрывает подсказку в реальном времени.
- **Рост банка заданий:** уровень 5 для senior, новые специализации, автоматический мониторинг утечки и «выбраковка» семейств.
- **PostgreSQL и очередь писем**, горизонтальное масштабирование (сейчас SQLite — один процесс).
- **Keycloak/OIDC ФСП** вместо проверки по e-mail (§7.3).

## 12. Известные ограничения

- Реестр ФСП — синтетический файл; интеграция проверена на контракте, не на реальном сервисе.
- Валидация — на модели; содержательную валидность тестов предстоит подтвердить на реальных данных (§6.5).
- Подсказка в реальном времени не устраняется; смягчается флагами и пониженным весом (§4.4).
- Категория «стажёр» и пул концептуальных вопросов — самая уязвимая к утечке часть банка (§6.4).
- SQLite и один процесс — достаточно для демонстрации и пилота, не для высокой нагрузки.
- Парсер PDF — эвристический: надёжно извлекает e-mail, телефон, стек из словаря; ФИО, опыт и роли — по шаблонным подписям, результат всегда проверяется кандидатом перед сохранением.
- Образ Docker не собирался в среде разработки (закрытый доступ к PyPI); версии зависимостей закреплены по установленным и проверенным локально, `gunicorn` — по номеру релиза.
